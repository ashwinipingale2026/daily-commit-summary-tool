# Daily Commit Summary Tool — Technical Specification

## 1. Purpose

A command-line tool for a Project Manager overseeing a 6-person team on a Time & Materials (T&M) project. It scans the local Git repository, collects commits made in the last 24 hours, and produces a Markdown report grouped by author — including an AI-generated plain-English summary of each author's changes and a simple activity indicator (Low/Medium/High) to support daily status visibility.

This tool is for **visibility only**. It does not calculate billable hours, does not integrate with time-tracking systems, and is not a substitute for timesheets.

## 2. Scope

### In scope
- Single local Git repository (this workspace: `module03-task`).
- Current/default branch only (e.g. `main`) — no scanning of other local or remote branches.
- Rolling 24-hour window (commits with a commit timestamp within the last 24 hours from the moment the tool runs).
- Manual, on-demand execution (run by the PM whenever a summary is needed). No scheduler/cron integration.
- Markdown report output, saved to disk.

### Out of scope
- Multiple repositories.
- Remote API integration with GitHub/GitLab/Azure DevOps (data is read entirely from the local `.git` history via `git log`).
- Author identity mapping/roster (git author name/email is used as-is).
- Billing/effort-to-hours conversion or time-tracking system integration.
- Automatic scheduling, email/Slack delivery, or a web UI.

## 3. Data Source & Collection

- Data is read from the local repository using `git log` (via `git` CLI subprocess calls, e.g. through Python's `subprocess` module or a lightweight wrapper).
- Window filter: `--since="24 hours ago"` (or equivalent explicit timestamp comparison) applied to the current branch (`HEAD`) only.
- For each commit collected, extract:
  - Commit hash (short)
  - Author name and email (as recorded by git — no external mapping)
  - Commit timestamp (author date, local timezone)
  - Commit message (subject + body)
  - Files changed (list + count)
  - Diff stats: lines added, lines removed (via `git show --stat` / `git log --numstat`)
- If the repository has **zero commits** in the last 24 hours, the tool skips report generation entirely (no file is written) and prints a message to the console (e.g. "No commits in the last 24 hours — report not generated.").
- If the repo has commits but a given author has none in the window, that author is simply omitted from the report (not listed with a zero row).

## 4. Report Structure (Markdown Output)

**Location:** `reports/commit_summary_<YYYY-MM-DD>.md` (date = date the report is generated, local time). The `reports/` directory is created automatically if it doesn't exist.

**Content outline:**

```markdown
# Daily Commit Summary — <YYYY-MM-DD>

Repository: module03-task
Branch: main
Window: <start timestamp> → <end timestamp> (last 24 hours)
Total commits: <N>
Contributing authors: <N>

## Author: <name> <<email>>
Activity: **High** | Commits: 5 | Files touched: 8 | Lines: +240 / -35

### Summary of changes
<AI-generated 2-4 sentence plain-English summary of what this author worked on,
synthesized from their commit messages and diffs>

### Commits
- `abc1234` (14:32) — <commit message subject>
  - Files changed: 3 | +80 / -10
- `def5678` (10:05) — <commit message subject>
  - Files changed: 2 | +15 / -2

---

## Author: <next author> ...
```

Authors are ordered by activity score (descending), then alphabetically as a tiebreak.

## 5. Activity Indicator (Low / Medium / High)

A simple weighted score is computed per author from data already collected (no external input required):

```
score = (commits * 3) + (files_touched * 1) + (lines_changed * 0.1)
```
where `lines_changed = lines_added + lines_removed`.

Thresholds (initial defaults, tunable via config):
- `score < 10` → **Low**
- `10 <= score < 30` → **Medium**
- `score >= 30` → **High**

Raw numbers (commit count, files touched, lines +/-) are always shown alongside the label so the derived score is never the only data point.

## 6. AI-Generated Change Summaries

Each author's "Summary of changes" section is generated by an LLM call:

- **Provider:** GitHub Models API.
- **Input to the model per author:** concatenated commit messages + truncated/aggregated diff content (or file-level diff stats if full diffs are too large) for that author's commits in the window.
- **Prompt intent:** "Given these commit messages and diffs, write a brief (2-4 sentence) plain-English summary of what this person worked on today, suitable for a project manager status report. Do not invent details not present in the input."
- **Output:** plain text, inserted directly into the report under each author's section.
- **Truncation/limits:** if diff content exceeds a configurable size limit, only file names + stat summaries are sent instead of full diffs, to keep prompt size manageable.
- **Failure handling:** if the API call fails (auth error, network error, rate limit) for a given author, the tool inserts a fallback line: `_AI summary unavailable — see commit list below._` and continues processing other authors and finishes the report (a single API failure does not abort the whole run).

## 7. Configuration & Credentials

- Credentials (GitHub Models API token) are supplied via a `.env` file at the project root, loaded with `python-dotenv`.
  - Expected variable: `GITHUB_TOKEN` (or `GITHUB_MODELS_TOKEN` — name finalized during implementation).
  - `.env` must be added to `.gitignore` so the token is never committed.
  - A `.env.example` file (with placeholder values, no real secrets) is committed instead, documenting required variables.
- Other tunables (time window hours, activity score thresholds, output directory, diff size limit) are configurable via constants at the top of the script or a small `config.py`, not hardcoded deep in logic.

## 8. CLI Usage

```
python summarize_commits.py
```

- No arguments required for the default behavior (current repo, current branch, last 24 hours).
- Console output on run:
  - Confirmation of repo/branch detected.
  - Number of commits found.
  - Path to the generated report file, or the "no commits" message if skipped.
  - Any per-author AI summary failures (logged as warnings, not fatal).

## 9. Error Handling

| Condition | Behavior |
|---|---|
| Not run inside a git repository | Print clear error and exit non-zero. |
| No commits in last 24 hours | Skip report generation, print info message, exit 0. |
| Missing/invalid API token | Print warning, proceed with reports using fallback text for all AI summaries. |
| LLM API call fails for one author | Log warning, use fallback text for that author only, continue. |
| `git` CLI not available on PATH | Print clear error and exit non-zero. |

## 10. Security Considerations

- API token is never logged, printed, or written into the generated report.
- `.env` is excluded from version control via `.gitignore`.
- Diff content sent to the LLM is limited to this repository's own commit data (no external/user-supplied input is passed through unsanitized to shell commands — all `git` invocations use argument lists, not shell string interpolation, to avoid command injection).
